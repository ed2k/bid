## §6.89 — extending the retarget to the other two slices: null

Tried the §6.88 procedure on `later_cont` and `open_uncont`. Both dead
ends, and the reason is the useful part.

**Harness trap (cost me one wasted run).** `--prefix` selects which RULES
are rewritten; `--only-group` selects which ROWS are featurised. They are
independent flags. Default `--only-group False,False` = `later_uncont`, so
`--prefix BD_later_cont_` scores **0 rows** and prints "77882 no leaf"
instead of failing. Mapping (from the rule conditions themselves):

    BD_later_uncont_  752 rules  ->  --only-group False,False
    BD_later_cont_    829 rules  ->  --only-group False,True
    BD_open_uncont_   252 rules  ->  --only-group True,False

**Ceiling vs realised, all three slices (same one-step metric):**

    slice           rows     leaves  ceiling(leaf_best-Brill)  oracle-Brill  realised
    later_uncont    77,482   762     +0.396                    +4.586        +0.082 +/- 0.020
    later_cont     187,628   829     +0.092                    +2.988        +0.005 +/- 0.049
    open_uncont     65,048   252     +0.021                    +4.309        14 leaves, not measured

`shipdd_c` = shipdd + 279/829 contested leaves (verified one-component:
all 279 changes in BD_later_cont_). Head-to-head vs shipdd, 6 seeds x
1500: +0.11, -0.00, -0.16, -0.08, +0.17, -0.01 →
**POOLED +0.005 +/- 0.049, t +0.10, CI [-0.092, +0.102], 2 up / 3 down.**
Doubles were deliberately LEFT IN here (opponents have bid, so X is legal
and is a real call; leaf_best picks X on 14% of rows vs Brill's 4%) — it
changed nothing.

**Why:** realised tracks the ceiling, and the ceiling is where one-step
lookahead is valid. In later_uncont the call you choose IS the contract
(94% of Brill's bids become final), so "score as if the auction stopped
here" is nearly true. An opening bid never is.

**But believe the oracle column, not the ceiling:** openings have the
LARGEST oracle gap (+4.309) and the smallest reachable ceiling. The
ceiling bounds what *this procedure* can find, not what exists. Openings
need a finer partition (8.2 distinct best calls per leaf), not a better
call per leaf.

**"Within-leaf agreement" is not a heterogeneity signal by itself.**
open_uncont has the LOWEST agreement (28.6%) and the SMALLEST ceiling — a
near-tied metric makes the argmax arbitrary: high apparent disagreement,
zero gain. later_uncont is the only slice with both (45.3%).

**Two to-dos closed:**
- `--relabel-dd-candidates {observed,bids,legal}` now declared (was
  "whatever Brill happened to do in this leaf"). Tests pin the canonical
  spelling trap: the pool must be `1S` not `1SPADES`, or a candidate is
  never `== str(node.prediction)` and reads as a change where it is the
  same call (and misses the margin guard). Legality is cached per position
  (auction-only, not deal-dependent).
- §6.82's outcome label needs no X/XX re-run: `relab` (78) and
  `relab_m300` (15) flip **zero** leaves to a double vs `dd`/`ddimp`'s 12
  each. Removing a never-selected candidate cannot move an argmax.

**Refines §6.87:** all 12 costly flips are to **XX**, not X. And
`opponents_bid` counts bids only (`features.py:363`:
`any(c.type == CallType.BID ...)`), so in later_uncont a redouble is legal
only where an opponent doubled without ever bidding — at the rest
`DecisionNet.actions` drops it and plays PASS.

**Conclusion: don't extend the retarget further.** It's a later_uncont
effect. 437 tests pass.

## §6.90 — the gain transfers to a different opponent

Blocking question was transfer: §6.88's +0.082 used `shipped` as the
opponent, so the gain could in principle be matchup-specific.

**A Brill run cannot answer it.** `--remote-a` ≈ 7.4 s/board; paired SE

boards (~20 h) × two arms. It would produce a new central number, not a
verdict on the change. That is why it stays un-run.

**Cheap substitute that does answer it:** play BOTH arms against the same
third opponent (`champion_system`) on the same deals, then difference
per-board. The deal and the opponent cancel.

## The 431-vs-404 vocab mismatch: resolved, and it is NOT a bug

I flagged this during the cleanup as possible breakage. It is by design.
Correcting my own alarm:

- `build_frozen_vocab()` = 431. It unions all 129 `BridgeFeatures` keys
  because the **dataset** encodes rule constraints as text containing
  feature *names*. `data/cot_dataset/vocab.json` is also 431 and IS guarded
  by `test_frozen_vocab_file_integrity`. Canonical.
- `data/cot_model/ckpt.pt.vocab.json` = 404 — a sidecar written at training
  time (`cot_model.py:194`). 431 is a strict superset: **27 added, 0
  removed**. The 27 are exactly the features added after ckpt.pt was trained
  (`agreed_trump*`, `*_is_longest`, `*_realsolid`, `partner_hcp_*`,
  `combined_hcp_*`, `*_first_call`, `opening_bid`, `rule20_total`,
  `rule_of_21`, `keycard_count_agreed`, `has_trump_*`).
- `cmd_generate` reads the vocab from the **dataset**, and
  `_grow_vocab_tensors` grows a smaller checkpoint's embedding/head to fit.
  A 404 ckpt against a 431 vocab is the intended path.
- `cot_export_web.py` defaults `--vocab` to the sidecar, which is why
  `manifest.json` says 404. Self-consistent.
- `mine_disagreements` loads the sidecar but only builds prompts via
  `format_state_prefix` (STATE/seat/AUCTION/HAND — no feature names).
  Verified: all 30 atoms in a real state prefix are known to both vocabs.

The 404 sidecar *does* raise on the new names if you encode constraints with
it — I reproduced `KeyError: Unseen token 'rule20_total'`. It just never
gets asked.

**Residual hazard, left alone:** `mine_disagreements.prefix_ids` uses
`if t in V` (silent drop) where `encode_line(strict=True)` raises. If
`format_state_prefix` ever emits a feature name, the student degrades
quietly instead of failing. Worth a strict check there if that changes.

Lesson: "two numbers disagree" is not "one of them is wrong". The sidecar
is *stale by design*; the authoritative vocab is the dataset one.

## Repo cleanup, part 3: the oversized JSONL is out of history

`git push` was rejected by GitHub: `data/brill_traces_578k.jsonl` is
**147 MiB** (154.24 MB decimal) against a 100 MB per-file cap.

Diagnosis before acting:

- It is the **only** blob over 100 MB, and it is reachable **only from
  unpushed commits** — added by `f2a7ff5`, removed by `c380b29`. Both sit
  inside `origin/main..main` (34 commits). Nothing on `origin` needs it.
- `origin/main` already carries 88.09 / 52.67 / 35.42 MB traces; all under
  the cap and already accepted.

First attempt — **wrong scope.** I ran a full-history
`git filter-branch ... -- main`, which rewrote all 150 commits including the
116 already published. Because the purge glob `brill_traces*.jsonl` also
matches the traces on `origin`, that rewrite **diverged published history**:
`git merge-base --is-ancestor origin/main main` → exit 1. It would have
needed `--force` and broken every clone. Reverted with
`git reset --hard backup/pre-rewrite-20260922`.

Correct scope: rewrite only `origin/main..main`. `origin/main` then stays an
ancestor and the push is an ordinary fast-forward.

    git filter-branch --force --prune-empty \
      --index-filter '/bin/sh /tmp/purge_index.sh' -- origin/main..main

(filter-branch accepts a rev-list range and rewrites only the positive side:
38 s for 34 commits vs 2 m 19 s for 150.)

Verified after:

- `origin/main` is an ancestor again → **no force-push**.
- No blob >100 MB reachable from `main`.
- `git diff backup/pre-rewrite-20260922 main` **empty** → content unchanged.
- 147 commits (3 empty ones pruned), 31 ahead of origin.
- The 147 MB file is still on disk, untracked.

Cleaned up `.git-rewrite/` and `refs/original/` — filter-branch leaves both,
and `refs/original` also pins the old objects.

**Lesson: scope a history rewrite to the unpushed range.** `-- main` rewrites
published commits and silently turns a fast-forward into a force-push. Always
check `git merge-base --is-ancestor origin/main main` after a rewrite — it is
the one-line test for "did I just break everyone's clone".

Also: filter-branch was the only option available — `git filter-repo` is not
on PATH and not importable here.

Also consolidated `MEMORY.md` (335 → 102 lines): it had outgrown the
injection limit and was being truncated on load.
